# Session Context, Context Overflow & Multi-Agent Spawning

> Design + investigation document for Forge Agent.
> Covers the `/compact` interjection question, the proposed `SESSION_CONTEXT.md`
> and `FORGE_TODO.md` workflow, the `-a` / `--auto` flag, and whether one agent
> instance can spawn/control another while sharing a Chromium window.

## 1. How sessions work today (baseline)

### 1.1 `-s` / `--session` takes a NAME, not a directory

In `src/index.js` an IIFE (`parseInstanceArgs`) runs **before** `config.js` is
required, because `config.js` reads `process.env.FORGE_SESSION_DIR` at module
load time.

Resolution order:

1. `--session-dir <path>` -> `FORGE_SESSION_DIR = resolve(path)`,
   `FORGE_SESSION_NAME = basename(path)`
2. `--session auto` / `--new-session` / `--random-session` -> generate a unique
   human-readable name (e.g. `brave-otter-9f3a`) via
   `registry.generateSessionName()`
3. `--session <name>` -> `FORGE_SESSION_DIR = sessionDirFor(name)`,
   `FORGE_SESSION_NAME = name`
4. `FORGE_ROLE = --role <name>` value, else defaults to the session name.

## 2. The context-drift / overflow problem

Web-model chats (DeepSeek/ChatGPT/Gemini) have a finite context window. When it
fills, the model silently drops or compresses older turns and **forgets decisions
made earlier** - this is the "drift" you described. Even with Forge's in-memory
`ConversationManager`, the *remote* model can forget, and Forge's own summaries
are lossy.

The durable fix is an **on-disk, always-current session context file** that:

1. Records what is being done, the discussions, and the decisions.
2. Survives remote context compaction - you can re-feed it after a `/clear`.
3. Is rewritten as commits/reverts happen so it reflects current state.
4. Is **never committed** and is removed at session end.

## 3. Feature: `SESSION_CONTEXT.md` (working memory on disk)

### 3.1 Purpose

A gitignored, auto-maintained markdown file at the project root that acts as the
agent's **durable working memory** for the current session.

### 3.2 Lifecycle

    SESSION START
      - create SESSION_CONTEXT.md (if absent) with a header + empty sections

    DURING SESSION
      - after each tool batch / decision: append or update the relevant section
      - on git commit : rewrite the "Current State" section to match HEAD
      - on git revert : rewrite the same section to match the reverted state

    SESSION END
      - delete SESSION_CONTEXT.md  (cleanup)

### 3.3 File template

    <!-- AUTO-GENERATED by Forge Agent. DO NOT COMMIT. Deleted at session end. -->
    # SESSION_CONTEXT - <session-name>

    - Session : brave-otter-9f3a
    - Started : 2026-10-06T09:20:00Z
    - Working : D:\puneet\Projects\forge-agent
    - Task    : "fix failing auth tests"

    ## Goal
    <one-line restatement of the task>

    ## Decisions
    - [09:22] Chose to mock the network layer instead of hitting the real API.
    - [09:31] Renamed login() -> authenticate() across src/auth/*.

    ## Progress
    - [x] Read tests/auth.test.js
    - [x] Identified failing assertion on line 42
    - [ ] Apply fix
    - [ ] Re-run tests

    ## Current State (auto-synced with git)
    - Branch : main
    - HEAD   : a1b2c3d "wip: auth refactor"
    - Dirty  : src/auth/login.js, tests/auth.test.js

    ## Open Questions
    - Should we keep the legacy login() shim?

### 3.4 Who writes it

- **The agent** (deterministic hook), not the model, for the structural parts
  (git state, timestamps, file lists).
- **The model** may propose bullet lines (decisions/progress) which Forge appends
  under the matching heading.

A small module, e.g. `src/session-context.js`, would own create/update/delete and
be called from `agent.js` at: session start, after each tool batch, after git
tool calls, and at shutdown.

### 3.5 Git-ignore

`.gitignore` must contain:

    SESSION_CONTEXT.md
    FORGE_TODO.md        # optional, if you want TODO state ignored too

Forge should **verify** the entry exists at session start and add it if missing
(or at least warn), so the file can never be accidentally committed.

### 3.6 Re-feeding after compaction

After a remote `/compact` or `/clear`, Forge reads `SESSION_CONTEXT.md` and
prepends it to the next message. This is the key trick: the model can forget,
but the file remembers.

## 4. Feature: `FORGE_TODO.md` (cross-session task queue)

Unlike `SESSION_CONTEXT.md` (ephemeral, deleted at end), `FORGE_TODO.md` is a
**persistent, human-authored** task list that may be committed.

### 4.1 Startup check

At session start the agent checks the current directory for:

- `FORGE_TODO.md`
- `SESSION_CONTEXT.md`

If **either** exists, it prints a notice and asks:

    Pending work detected:
      - FORGE_TODO.md      - 3 open items
      - SESSION_CONTEXT.md - previous session 'brave-otter-9f3a' (ended 2h ago)

    Continue from this work? [y/N]

- **No** -> start fresh (and, for a stale `SESSION_CONTEXT.md`, offer to delete it).
- **Yes** -> load them as context and resume.

## 5. Feature: `-a` / `--auto` (unattended TODO execution)

### 5.1 Semantics

`-a` / `--auto` tells Forge to **start working on `FORGE_TODO.md` items without
any user intervention**.

Crucial constraint: **auto mode applies to `FORGE_TODO.md` only - never to
`SESSION_CONTEXT.md`.** A `SESSION_CONTEXT.md` is advisory context; it must not
silently drive autonomous action, because it may describe half-finished or
abandoned work.

### 5.2 Behavior matrix

| FORGE_TODO.md | SESSION_CONTEXT.md | Flag | Behavior |
|---|---|---|---|
| absent | absent | - | Normal run. |
| present | absent | - | Prompt: "pending TODO - continue? [y/N]" |
| present | absent | -a | **Auto-start** on TODO items. No prompt. |
| present | present | - | Prompt for both; on yes load both. |
| present | present | -a | Auto-start on **TODO only**; SESSION_CONTEXT loaded read-only, never auto-acted on. |
| absent | present | -a | Nothing for auto to act on -> normal run; SESSION_CONTEXT context only. |
| absent | present | - | Prompt: "stale session context - resume or discard?" |

### 5.3 Ordering & guardrails in auto mode

- Process TODO items **top-to-bottom**, marking each `[ ]` -> `[x]` as completed.
- Stop on the first item that fails or needs a human decision, and **halt**
  (do not churn) - leaving `FORGE_TODO.md` accurate for the next run.
- Auto mode still respects all sandbox/permission rules.
- Auto mode never touches files outside the project root unless the TODO item
  explicitly names them.
- `--auto` refuses to run if `FORGE_TODO.md` is absent **and** no task was given
  (nothing to do -> exit 0 with a message).

## 6. Can one agent instance spawn and control another?

### 6.1 Current state - yes for spawning, partial for control

- **Spawning:** Every invocation of `forge-agent ... --session <name>` already
  starts a fully independent process with its own browser profile. You can spawn
  them today with your shell (or `start_process` in the agent toolbox).
- **Discovery/control:** `src/session-registry.js` writes an `instance.json`
  heartbeat per session and can list live instances (`ps`). There is **no**
  built-in "spawn child and manage its lifecycle" API yet - you'd shell out.

### 6.2 Shared Chromium window/session?

Short answer: **not safely, no** - and it's usually the wrong design.

- `chromium.launchPersistentContext(sessionDir, ...)` takes an **exclusive lock**
  on the profile directory. Two processes pointed at the *same* `sessionDir` will
  conflict (second launch fails or corrupts the profile).
- Therefore each agent instance **must** use a distinct `--session` (distinct
  profile dir). That is exactly why session isolation exists.
- To *share* a single browser you would need a **browser broker**: one process
  owns the `BrowserContext`/pages and other agents connect via CDP or IPC and
  request pages. Playwright supports `connectOverCDP`, but a single chat page can
  only hold one conversation, so N agents on one page would interleave messages -
  not viable.

**Recommendation:** keep one Chromium profile per session; share *data*
(files, `SESSION_CONTEXT.md`, `FORGE_TODO.md`), not the browser.

### 6.3 Proposed supervisor/child model (aligns with ROADMAP v2.0 "Supervisor Mode")

    Supervisor agent (session: boss)
      - spawn child A (session: worker-a) : task "write tests"
      - spawn child B (session: worker-b) : task "refactor auth"
      - wait / poll child heartbeats (session-registry.listInstances)
      - read each child's SESSION_CONTEXT.md for progress
      - kill children when their FORGE_TODO slice is done

Lifecycle primitives needed:

| Action | Primitive | Notes |
|---|---|---|
| create | spawn({ session, task, role }) | shell out / child_process; distinct profile |
| provide context | write a scoped SESSION_CONTEXT.md or pass FORGE_TODO.md slice | file-based handoff |
| monitor | listInstances() + read child SESSION_CONTEXT.md | already partially available |
| kill | stopProcess(name) / kill PID from instance.json | PID is recorded |
| cleanup | each child deletes its own SESSION_CONTEXT.md at end | |

### 6.4 Answer to "share Chromium window and session?"

- **Same window/session: no** (profile lock + single conversation per page).
- **Shared files/context: yes** - that is the correct coordination channel.
- If you truly need one visible window, run one browser and have agents talk to a
  broker; treat it as a v2+ research item, not a quick flag.

## 8. Suggested implementation order

1. **Docs + help fix** - clarify name-vs-directory, de-duplicate help/`parseArgs`.
2. **`src/session-context.js`** - create/update/delete `SESSION_CONTEXT.md`;
   wire create at start, update after tool batches & git ops, delete at shutdown.
3. **`.gitignore` guard** - ensure `SESSION_CONTEXT.md` / `FORGE_TODO.md` ignored;
   auto-add with a warning if missing.
4. **Startup prompt** - detect `FORGE_TODO.md` / `SESSION_CONTEXT.md`, ask to resume.
5. **`-a` / `--auto`** - TODO-only unattended execution with halt-on-failure.
6. **Supervisor spawning** - a thin `spawn_agent` tool wrapping child_process +
   `session-registry`, with monitor/kill - matches ROADMAP v2.0.
