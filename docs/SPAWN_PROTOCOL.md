# Forge Agent — Parent/Child Spawn Protocol

> Version: 1.0
> Status: Normative. Any change to spawn behaviour MUST update this document.
>
> This document defines how a **parent** Forge Agent instance spawns, identifies,
> monitors, and controls **child** Forge Agent instances. It is the single source
> of truth for the spawn contract. Code lives in `src/agent-supervisor.js`,
> `src/session-registry.js`, `src/spawn-task.js` and the `spawn_agent` /
> `list_agents` / `kill_agent` tools in `src/tools.js`.

---

## 1. Goals

1. A child MUST run in its **own window** (own terminal), never inline in the
   parent's command window, so the parent stays usable and output never mixes.
2. The parent MUST **hold the child's PID** and be able to control its lifecycle
   (query liveness, gracefully stop, force kill).
3. Each child MUST get an **independent session** (own Chromium profile dir) and
   a **limited, explicitly assigned task**.
4. Each child MUST have a unique **identifier** and a task-definition markdown
   file (like a forge plan) in which finished tasks/subtasks are marked.
5. The child's **window title** MUST contain its identifier so a human can find
   it among many windows.
6. Parent and child MUST exchange **heartbeats** so the parent always knows
   whether a child is alive, unresponsive, or dead.
7. `ps` / `list_agents` MUST list parents **and** children and show the
   **parent→child relationship** (machine-readable, for a future UI).

---

## 2. Identifier

Every spawned child has one canonical identifier:

```
forge-<session>-<pid>
```

- `<session>` — the child's session name, sanitised to `[A-Za-z0-9._-]`.
- `<pid>` — the child's OS process id, assigned by the OS at spawn time.

Example: `forge-worker-auth-41232`.

Because the PID is only known after spawn, the parent writes a provisional
record keyed by session name first and **upgrades** it to the full identifier
once the OS returns the PID. The identifier is then written into:

- the child's registry record (`identifier` field),
- the child's task file (`SESSION_TASK.md`),
- the child's window title,
- the environment variable `FORGE_CHILD_ID` handed to the child.

---

## 3. Spawn contract (new window)

`spawnAgent(opts)` launches the child **detached in a new terminal window**.

| Platform | Mechanism |
|----------|-----------|
| win32    | `cmd.exe /c start "<title>" <node> <entry> <args...>` |
| darwin   | `osascript` → `Terminal` `do script` |
| linux    | first available of `x-terminal-emulator`, `gnome-terminal`, `konsole`, `xterm` with `-e` |

If a terminal emulator cannot be found, the supervisor falls back to a headless
detached spawn (no visible window) and records `window: "headless"` in the
registry — the PID/heartbeat/kill contract still holds.

### 3.1 Environment handed to the child

| Variable | Meaning |
|----------|---------|
| `FORGE_SESSION_NAME` | child session name |
| `FORGE_SESSION_DIR`  | child profile dir |
| `FORGE_ROLE`         | role label |
| `FORGE_PARENT_ID`    | parent's `FORGE_SESSION_NAME` (may be empty for a root) |
| `FORGE_PARENT_PID`   | parent's OS pid |
| `FORGE_CHILD_ID`     | full child identifier (set by the launcher wrapper) |
| `FORGE_TASK_FILE`    | absolute path to the child's `SESSION_TASK.md` |
| `FORGE_HOME`         | inherited, so registry is shared |

`FORGE_PARENT_PID` and `FORGE_PARENT_ID` are what make the **relationship**
visible in `ps` / `list_agents` and available to a future UI.

## 4. Child task file — `SESSION_TASK.md`

Generated by the parent at spawn time (module `src/spawn-task.js`). It is a
forge-plan-style markdown file, scoped to the child.

### 4.0 One file per instance (NEVER shared)

Because several children can run in the SAME working directory, each child gets
its **own** task file — there is **no shared `<cwd>/SESSION_TASK.md`**. The path
is resolved per instance (`spawnTask.instanceTaskPath`), in this order:

1. an explicit `opts.taskFile` (caller override), else
2. `<FORGE_HOME>/sessions/<session>/SESSION_TASK.md` — **the default**, unique
   to the child's session dir (outside the repo, so no `.gitignore` churn), else
3. `<cwd>/<identifier>.SESSION_TASK.md` (fallback if no session dir is known).

The resolved path is recorded in the registry (`taskFile`) and handed to the
child as `FORGE_TASK_FILE`. The child's scoped `SESSION_CONTEXT.md` likewise
lives inside its own session dir, so two children never share context either.

Template:

```markdown
<!-- AUTO-GENERATED by Forge Agent supervisor. Do not commit. -->
# SESSION_TASK — forge-<session>-<pid>

- Session   : <session>
- Parent    : <parent-session> (pid <parent-pid>)
- Role      : <role>
- Created   : <ISO timestamp>
- Working   : <cwd>

## Assigned task

<the task string>

## Subtasks

- [ ] <subtask 1>
- [ ] <subtask 2>

## Handed-off context

<context lines, if any>

## Progress log

- [<HH:MM>] spawned
```

### 4.1 Marking finished work

- The child marks a subtask done by rewriting `- [ ]` to `- [x]` for that line.
- The child appends progress-log lines: `- [HH:MM] <what happened>`.
- On completion the child appends `- [HH:MM] TASK_COMPLETE` and sets its
  registry `status` to `completed`.

### 4.2 Reading progress

The parent reads `SESSION_TASK.md` from disk (via `readChildTask`). The
checkboxes are the authoritative progress signal; the registry heartbeat is the
liveness signal. They are deliberately separate.

## 5. Registry record (heartbeat)

One JSON file per instance at `<FORGE_HOME>/instances/<session>.json`:

```json
{
  "id": "worker-auth",
  "name": "worker-auth",
  "identifier": "forge-worker-auth-41232",
  "role": "worker-auth",
  "pid": 41232,
  "ppid": 39800,
  "parentId": "brave-otter-9f3a",
  "parentPid": 39800,
  "isChild": true,
  "window": "new",
  "taskFile": "D:/proj/SESSION_TASK.md",
  "cwd": "D:/proj",
  "model": "deepseek",
  "profile": "default",
  "status": "running",
  "startedAt": 1731300000000,
  "lastHeartbeat": 1731300005000,
  "sessionDir": "..."
}
```

### 5.1 Heartbeat cadence

- The child writes a heartbeat on start (`starting`), after init (`running`),
  and then at least every `FORGE_HEARTBEAT_INTERVAL_MS` (default **5000 ms**).
- An instance whose `lastHeartbeat` is older than
  `FORGE_HEARTBEAT_TTL_MS` (default **20000 ms**, i.e. 4 missed beats) while its
  PID is still alive is classified **unresponsive**.
- An instance whose PID is gone is classified **dead** (stale record is pruned).

### 5.2 Status values

`starting` | `running` | `idle` | `unresponsive` | `completed` | `failed` | `killed`

## 6. Liveness & control

`classifyInstance(record)` returns one of:

| State | Condition |
|-------|-----------|
| `running` | PID alive and heartbeat fresh |
| `unresponsive` | PID alive but heartbeat older than TTL |
| `dead` | PID not alive |

### 6.1 Stop sequence (`killChild`)

1. Resolve target by identifier, session name, unique prefix, or numeric PID.
2. Refuse to kill a process that is not a known Forge instance unless
   `{ force: true }` is passed explicitly (safety).
3. Send graceful terminate (`SIGTERM` / on win32 `taskkill /PID <pid>`).
4. Poll for up to `graceMs` (default 5000 ms) for the PID to exit.
5. If still alive, force kill (`SIGKILL` / `taskkill /F /PID <pid>`).
6. Update the registry record to `killed` and run cleanup (see 6.2).

On win32 `terminate()` awaits the `taskkill` process so the poll after it is
reliable; both graceful and force steps are awaited before re-checking liveness.

### 6.2 Cleanup lifecycle (per child)

Every child owns per-instance artifacts that MUST be cleaned up when it reaches
a terminal state, so dead children never leak files:

| Artifact | Location | Removed by |
|----------|----------|------------|
| `SESSION_TASK.md` | child session dir (or `FORGE_TASK_FILE`) | child on clean exit; parent `cleanupChild` on kill/prune |
| `SESSION_CONTEXT.md` | child session dir | `agent.shutdown()` / dir removal |
| Chromium profile | `<FORGE_HOME>/sessions/<session>/` | `cleanupChild` (dir removal) |
| registry heartbeat | `<FORGE_HOME>/instances/<session>.json` | `removeHeartbeat` / `cleanupChild` |

Terminal states and who cleans up:

- **completed / clean exit** — the child removes its own task file on shutdown
  (it knows `FORGE_TASK_FILE`) and destroys its scoped `SESSION_CONTEXT.md`.
- **killed** — `killChild` calls `cleanupChild` by default (opt out with
  `{ cleanup: false }`), removing the task file, the whole session dir, and the
  registry heartbeat file.
- **crashed / orphaned (dead PID)** — `pruneOrphans()` scans the registry and
  runs `cleanupChild` for every record whose PID is dead. Live children are
  never touched (liveness is re-checked per record).

`cleanupChild(inst)` and `pruneOrphans()` are exported from
`src/agent-supervisor.js`; both are best-effort and never throw into the loop.

## 7. `ps` / `list_agents` output

The list is a flat set plus relationship metadata:

- Text table columns: `ID`, `ROLE`, `PID`, `PARENT`, `STATUS`, `BEAT`, `TASK`.
- `PARENT` shows the parent identifier (or `-` for a root instance).
- `BEAT` shows heartbeat age, e.g. `3s` / `24s`.
- `--json` emits the raw records including `parentId`, `parentPid`, `isChild`,
  so a UI can build a tree.

A helper `buildInstanceTree(instances)` returns
`[{ record, children: [...] }]` for UI consumption.

---

## 8. Strict rules (MUST)

1. A child MUST run in its own window when a terminal is available.
2. The parent MUST record and expose the child's PID and identifier.
3. The parent MUST be able to determine liveness from the registry alone.
4. The child MUST write a heartbeat while it runs.
5. The parent MUST gracefully terminate before force-killing.
6. `ps` MUST show parents and children and their relationship.
7. Every spawn MUST create a `SESSION_TASK.md`.
8. Every child MUST have its OWN task file (never a shared `<cwd>` file), so
   multiple children in the same cwd never collide.
9. A child's per-instance artifacts MUST be cleaned up at every terminal state
   (completed/killed/crashed) — via the child itself, `cleanupChild`, or
   `pruneOrphans`.
10. No component may throw into the agent loop on registry I/O failure
   (all registry operations are best-effort and never fatal).

## 10. Practical example — parallelizing read / write / test work

Forge Agent has **two independent kinds of parallelism**.

### 10.1 Mode A — parallel tool calls inside ONE agent

Within a single agent run, when the model emits a batch of independent tool
calls, `src/parallel-executor.js` (`executeBatch`) runs them concurrently (up to
`MAX_PARALLEL_TOOL_CALLS`, default **4**; disable with `PARALLEL_TOOL_CALLS=false`).
It is **dependency-aware**: each call reduces to conflict keys (a resolved file
path, or a `shell-ro`/`shell-rw` bucket). Calls sharing a key run in later waves
(after earlier ones); calls with no shared key run together. Many pure reads
(`read_file`, `search_in_files`, `git_diff`, …) run at once; two writes to the
same file are serialised; a non-read-only `run_command` is a global barrier.

### 10.2 Mode B — multiple child agents running concurrently

`spawn_agent` starts an independent child instance (own session, browser
profile, per-instance `SESSION_TASK.md`) that runs its own loop in its own
terminal window. N children make progress at the same time. Use this for long,
*independently shardable* work — not for two children editing the same file
(Forge has no cross-child file lock; partition the work).

### 10.3 Worked example — split a repo job across 3 children

Parent task: *"Harden auth: add tests, fix the login race, and document it. Do
the three pieces in parallel."*

```
spawn_agent { session:"worker-tests",      task:"Add tests for src/auth/*, iterate to green", subtasks:[...] }
  -> identifier: forge-worker-tests-41232  pid: 41232  window: new
     task file : <FORGE_HOME>/sessions/worker-tests/SESSION_TASK.md
spawn_agent { session:"worker-fix-login",  task:"Fix the login race in src/auth/login.js", subtasks:[...] }
spawn_agent { session:"worker-docs",       task:"Document the auth module in docs/auth.md", subtasks:[...] }

list_agents {}
  -> worker-docs      pid 41251  PARENT <id>  running  BEAT 1s
     worker-fix-login pid 41240  PARENT <id>  running  BEAT 2s
     worker-tests     pid 41232  PARENT <id>  running  BEAT 1s

read_agent_task { name:"worker-tests" }
  -> Progress : 2/4 subtasks done
     [x] enumerate auth functions
     [x] add tests
     [ ] run tests
     [ ] fix failures

(poll list_agents + read_agent_task until COMPLETE or heartbeat unresponsive)
kill_agent { name:"worker-tests" }   -> Stopped child agent (pid 41232).
```

| Need | Tool | Signal |
|------|------|--------|
| Is the child alive? | `list_agents` | STATUS (running/unresponsive/dead) + BEAT age |
| How far did it get? | `read_agent_task` | checked subtasks + progress log |
| Stop it | `kill_agent` | graceful then force by id/session/PID |
| Cleanup | automatic | child removes its file on exit; kill/prune clean leftovers |

Each child's `SESSION_TASK.md` lives in its own session dir, so
`read_agent_task` on one child never confuses it with another even though all
three run in the same repo.

### 10.4 Why not just spawn everything?

- Children are full browser-backed agents — heavier than a batched tool call.
  Use Mode A for many reads / independent quick calls; Mode B for long shards.
- No shared mutable workspace lock between children. Partition by files/modules;
  run same-file work sequentially or in one child.
- Coordination is files + registry, never the browser.
